# IMPLEMENTATION TASK: Automated Reports Management
## SEHC — AI Government Relations Intelligence Platform

OBJECTIVE
Implement a complete Automated Reports management page under the existing History Report module, containing three integrated tabs: Schedules, Recipient Groups, and Delivery History. Build a functional UI and configuration backend, not a static mockup. Do not implement LangGraph agents or actual email delivery yet.

1. INSPECT EXISTING PROJECT
Inspect the React/TypeScript frontend, Node.js/TypeScript backend, routing, History Report, New Government Meeting form, shared components, API conventions, schemas and JSON persistence. Existing structure includes apps/web, apps/api, packages/shared, packages/schemas, packages/db, data/vips.json and data/government_meetings.json. Reuse current conventions and dependencies.

2. NAVIGATION
History Report
  - Meeting Performance (existing History Report, unchanged)
  - Automated Reports (new)
Automated Reports contains internal horizontal tabs: Schedules, Recipient Groups, Delivery History. Breadcrumb: Home > History Report > Automated Reports. Title: Automated Reports. Subtitle: Schedule and distribute VIP meeting reports automatically. Support direct navigation to tabs.

3. VISUAL CONSISTENCY
Match the existing SEHC dark-blue government-themed top header, globe/building imagery, light-blue sidebar, blue/cyan active highlights, white/light-blue glass-style cards, gradients, typography, forms, tables, icons, badges and shadows. Do not introduce an unrelated template or replace the application shell. Ensure consistent spacing, responsive layout, empty/loading/error states across tabs.

4. SHARED SUMMARY CARDS
Show Active Schedules, Recipient Groups, Delivery Success Rate and Reports Sent This Month. Calculate from persisted data. Show 0 or N/A where appropriate, never fabricate success rates or trends. Keep cards visible and consistent across tabs.

5. TAB: SCHEDULES
Two-column layout. Left: searchable/filterable schedule list with name, type, active badge, recurrence, send time, group count, unique active recipient count, enable toggle, edit/duplicate/delete actions. Highlight selected item. Confirm deletion.
Right: Create/Edit Schedule form with Schedule Name (required, max 150), Report Type (central registry), Frequency (Daily/Weekly/Monthly), conditional Day of Week or Day of Month, Send Time, Timezone (default Asia/Ho_Chi_Minh), Enabled toggle, recipient group multi-select. Report types initially: VIP Meeting Status Report, VIP KPI Performance Report, Monthly Executive Summary, Media Event Report, Personnel Change Report. Support monthly Last Day and different month lengths.
Recipient selector searches existing groups, shows 'RG-001 — GR Management (5 recipients)', uses removable chips, supports multiple groups and shows deduplicated unique active recipient count. Do not require typing raw IDs. Persist stable recipient_group_ids rather than copied emails.
Actions: Cancel, Preview Email, Save Schedule, Send Now. Save validates fields and active groups/recipients, persists and refreshes. Preview uses explicitly labeled placeholder content and never sends. Disable Send Now until a real generator and delivery service are configured; never fake success. Distinguish enabled status from execution status. Calculate next run respecting timezone.

6. TAB: RECIPIENT GROUPS
Use same two-column design. Left: searchable group list, status filter, New Group, cards showing group ID, name, description, active member count, status and edit/delete. Right: editor with generated stable Group ID (read-only), unique Group Name (required), Description, Active/Inactive status and editable Members table.
Members fields: stable Recipient ID, Name, Email, Department, Active/Inactive status, actions. Support add/edit/remove/search. Validate emails, reject duplicates within group. Editing must preserve IDs. Show total/active/inactive member counts and referencing schedules. Inactive groups cannot be newly selected; inactive members are excluded from deliveries. Prevent hard deletion of referenced groups; offer deactivation. Renaming a group must not break schedule references. Changes to membership must affect future recipient resolution automatically.

7. TAB: DELIVERY HISTORY
Use shared card/table design. Filters: search, report type, schedule, status, date range, refresh. Table columns: Execution ID, Report Name, Trigger (Scheduled/Manual), Execution Time, Recipients, Status, Actions. Statuses: Queued, Running, Sent, Partially Failed, Failed, Cancelled. View Details modal/drawer: execution/schedule IDs, report type, trigger, start/end timestamps, recipient groups, resolved recipient count, success/failure counts, errors, report preview if available and per-recipient results if provided. Never show secrets. If no real executions exist, show 'No report deliveries yet' and explanation. Never seed fake production delivery records.
