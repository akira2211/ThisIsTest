SEHC Email Engine — Phase 1: Core Architecture & Report Registry

You are working on the existing SEHC AI Government Relations Intelligence Platform.

Objective

Build the foundation of a reusable, centralized Email Engine that supports multiple report types, HTML templates, scheduled execution, and a pluggable email delivery provider.

This phase must NOT send real emails.

Requirements

1. Inspect the current repository, including:
   
   - Automated Reports page
   - Schedules, Recipient Groups, Delivery History tabs
   - Existing Node.js backend and API conventions
   - Existing JSON persistence and shared schemas
   - Existing History Report KPI/business calculation services

2. Implement an Email Engine module with:
   
   - EmailEngine
   - ReportRegistry
   - ReportDefinition
   - ReportDataProvider interface
   - HtmlTemplateRenderer interface
   - EmailDeliveryAdapter interface
   - ReportExecutionContext
   - ReportExecutionResult

3. Support multiple report types through registration, without modifying the core engine when a new report is added.

4. Each ReportDefinition must identify:
   
   - report_type
   - display_name
   - description
   - template_id
   - data_provider
   - enabled
   - version

5. Implement a generic execution pipeline:
   
   Schedule/Manual Request
   → Validate Report Type
   → Load Report Definition
   → Prepare Execution Context
   → Load Data
   → Render HTML
   → Resolve Recipients
   → Delivery Adapter
   → Execution Result

6. Separate report generation from email delivery so the same report can be previewed without sending.

7. Integrate with existing report schedules using stable report_type identifiers.

8. Define strict TypeScript types and runtime validation.

9. Preserve the existing application architecture. Do not introduce unnecessary dependencies or a separate deployment.

10. Implement unit tests using mock data providers and mock delivery adapters.

Important Constraints

- Do not implement real SMTP or Agent Builder API calls.
- Do not implement the scheduler yet.
- Do not duplicate existing KPI calculation logic.
- Do not modify unrelated VIP or meeting business logic.
- Do not introduce LangGraph for deterministic email processing.
- Do not use hardcoded recipient addresses.

Deliverables

Implement the foundation directly in the repository. Provide modified files, architecture summary, public interfaces, test results, and integration points for Phase 2.

Do not stop at a design proposal.

SEHC Email Engine — Phase 3: Agent Builder Email API Integration

Continue from Phases 1 and 2.

Objective

Integrate the existing Agent Builder API as an email delivery adapter.

Existing API Request Pattern

const url =
  `${CONFIG.BASE_URL}/api/v1/run/${CONFIG.API_ENDPOINT}?stream=false`;

const payload = {
  input_type: "chat",
  output_type: "chat",
  input_value: CONFIG.INPUT_VALUE
};

const response = await fetch(url, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "x-api-key": CONFIG.API_KEY
  },
  body: JSON.stringify(payload)
});

Requirements

1. Implement AgentBuilderEmailAdapter behind the existing EmailDeliveryAdapter interface.

2. Configure:
   
   - Base URL
   - API endpoint
   - API key
   - Request timeout
   - Retry policy

3. Store credentials in server-side environment variables.

4. Support sending:
   
   - Email subject
   - HTML body
   - Recipient email addresses
   - Execution ID / correlation ID

5. IMPORTANT: Inspect or confirm the actual Agent Builder workflow contract before implementing payload mapping.
   
   Do not assume that input_value alone supports structured recipient, subject and HTML body fields.

6. Ensure the Agent Builder workflow sends HTML as the email HTML body, not as plain text.

7. Implement response parsing and error handling.

8. Distinguish:
   
   - Request accepted
   - Email send confirmed
   - Delivery confirmed, if supported
   - Failed
   - Unknown outcome

9. HTTP 200 alone must not be treated as proof of inbox delivery.

10. Support timeout handling, safe retry behavior and duplicate-send prevention.

11. Redact API keys and sensitive email content from application logs.

12. Implement integration tests using mocked API responses.

13. Provide a controlled manual test path using an explicitly configured test recipient.

Constraints

- Do not hardcode API keys.
- Do not expose credentials to React.
- Do not send emails to production recipient groups during tests.
- Do not change HTML rendering logic from Phase 2.
- Do not implement automatic scheduling yet.

Deliverables

Working Agent Builder Email Adapter, configuration documentation, error handling, integration tests and verified HTML email sending where a test endpoint is available.

If the actual workflow payload contract is unavailable, implement the adapter interface and mock tests, then clearly identify the missing contract rather than inventing fields.

SEHC Email Engine — Phase 4: Scheduler & Delivery History

Continue from Phases 1–3.

Objective

Enable automatic execution of configured report schedules using the existing Automated Reports management UI.

1. Scheduler

Support:

- Daily
- Weekly
- Monthly
- Timezone-aware execution
- Enable/disable schedules
- Last execution
- Next execution
- Manual Send Now

Use Asia/Ho_Chi_Minh as the default timezone.

Implement durable execution tracking.

Prevent duplicate executions when the service restarts or multiple workers are running.

Use an execution key based on schedule ID and scheduled occurrence.

2. Recipient Resolver

At execution time:

1. Load recipient_group_ids from the schedule.
2. Fetch current recipient groups.
3. Exclude inactive groups and members.
4. Validate email addresses.
5. Deduplicate recipients by normalized email.
6. Return the final recipient list.

Do not store duplicated recipient email lists inside schedules.

If no valid recipients exist, mark the execution as failed or skipped with an explicit reason.

3. Execution Flow

Scheduler
→ Create Execution
→ Load Report Definition
→ Collect Report Data
→ Render HTML
→ Resolve Recipients
→ Send via Agent Builder Adapter
→ Record Results

4. Delivery History

Persist:

- execution_id
- schedule_id
- report_type
- template_version
- trigger_type
- scheduled_at
- started_at
- completed_at
- status
- recipient count
- success count
- failure count
- provider response metadata
- error details

Use the existing Delivery History tab.

Support real filtering, searching and execution details.

Do not create fake successful deliveries.

5. Failure Handling

Implement:

- Configurable timeout
- Bounded retry
- Retry backoff
- Safe duplicate prevention
- Execution logging
- Error classification
- Manual retry where safe

Do not automatically retry an uncertain send outcome unless provider idempotency or delivery reconciliation makes it safe.

6. UI Integration

Update:

- Active schedule status
- Last run
- Next run
- Send Now
- Delivery History
- Reports Sent KPI
- Delivery Success Rate KPI

Ensure the UI displays actual backend data.

7. Tests

Test:

- Daily/weekly/monthly triggers
- Restart recovery
- Duplicate execution prevention
- Inactive schedules
- Recipient deduplication
- Empty recipient groups
- Provider failures
- Timeout behavior
- Manual Send Now
- Delivery History persistence

Deliverables

A working scheduler, recipient resolver, execution manager and integrated Delivery History.

Run available tests and build successfully.

5. Hai điểm cần đặc biệt chú ý
Thứ nhất — API hiện tại. Bạn đã có Agent Builder API gọi bằng input_value. Nhưng để triển khai Phase 3 chính xác, cần xác định workflow đó nhận subject, recipient list và HTML body như thế nào. Nếu workflow chỉ nhận một chuỗi, chúng ta có thể cần quy định một JSON envelope trong input_value, đồng thời cập nhật workflow để parse nó.
Thứ hai — Template HTML. Không nên cho mỗi schedule sở hữu một bản HTML riêng. Schedule chỉ tham chiếu report_type; Report Registry xác định template và data provider. Một template có thể phục vụ nhiều schedule khác nhau, mỗi schedule có lịch gửi và recipient groups riêng.
Tôi khuyên bắt đầu Phase 1 và Phase 2 trước. Sau hai phase đó, bạn sẽ có nền tảng Email Engine và một HTML report hoàn chỉnh, xem được bằng nút Preview Email mà chưa cần kích hoạt việc gửi mail thực tế.
